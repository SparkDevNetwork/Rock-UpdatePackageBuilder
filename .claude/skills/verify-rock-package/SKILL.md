# Verify a Rock update package

The builder diffs a base version against the target and ships only the files that differ. The package's required
version is a minimum, so any site at or above it can install. A site on a version other than the base can end up with
mismatched files: for example a new `.ascx.cs` next to an old `.ascx`, which fails at runtime with CS0103.

A package built from base B is correct for a site on version V when no file is the same in B and the target but
different on V. Release dates and git ancestry don't prove this; only a file check does.

## Rules

1. **Build from the required version.** The builder's `--lastVersionTag` and `--previousVersionRockWebFolderPath` must
   both be the required version. Never build from a newer version than the minimum.
2. **Choosing the minimum is a policy call** (e.g. the last release of the previous major shipped before the next
   major's first release). Accept what the packager gives; verify it, don't argue it.
3. **The allowed releases** are every release from the minimum up to the target, including releases of an earlier major
   that ship alongside it (e.g. 18.8 next to 19.8).
4. **Zero missing files on every allowed release** is the bar. Report results in a short table; lead with pass or fail.

## Step 1: Confirm the inputs

Fill in every answer this conversation already establishes (versions, paths, the package, earlier results). Use the
defaults in brackets for the rest. Show all of them in one block, mark which ones you filled in, and ask the packager to
correct anything and say when to start. Ask only for answers you can't fill in.

1. **Target version and release tag**, e.g. `19.8` and `19.8.1-alpha` [the newest tag from
   `git -C <checkout> tag -l '<target>.*' --sort=-v:refname`]. Every package being verified has one.
2. **Required (minimum) version tag**, e.g. `18.2.4`.
3. **Simulate or check a built package?** Simulate before building; check the `.rockpkg` after
   [`D:\source\rock\_Apps\Rock-UpdatePackageBuilder\RockPackages\<target>.rockpkg` if it exists].
4. **Rock checkout** with tags fetched [`D:\source\rock\Rock-packaging`], with the target tag's files checked out.
5. **Compiled RockWeb of the target** [`<checkout>\RockWeb`]: the Release build the package came from. It separates
   generated files from real leftovers.
6. **Sibling release tags**: other majors' releases shipping at the same time [their newest tags, e.g.
   `18.8.1-alpha` for 19.8]. Pre-release tags are otherwise skipped, so these must be named.
7. **Pre-release tags to skip** [`^(1\.17\.|18\.0\.)`: 17.0 pre-releases and 18.0, which never shipped]. Tags ending in
   `-alpha`, `-beta` or `-pre` are skipped automatically. Ask before skipping anything else.

Check before running: `git -C <checkout> tag -l <minimum> <target tag> <sibling tags>` prints every tag; if not, ask
them to `git fetch --tags`.

## Step 2: Run

```bash
bash .claude/skills/verify-rock-package/verify-package.sh \
    -r /d/source/rock/Rock-packaging -m 18.2.4 -t 19.8.1-alpha -v 19.8 \
    -x '^(1\.17\.|18\.0\.)' -s 18.8.1-alpha -w /d/source/rock/Rock-packaging/RockWeb \
    -p RockPackages/19.8.rockpkg -o <scratchpad>/verify-19.8
```

Leave out `-p` to simulate. It takes about a minute, reads the package without changing it, and exits 1 on any
failure.

## Step 3: Explain the result

The release table:

| Column | Meaning | Action |
|---|---|---|
| Missing | Files the site has wrong after install | Must be 0. Otherwise the base is wrong; rebuild. |
| Stale | Files left behind that the target removed | `.ascx` / `.ascx.cs` pairs are usually removed by the chop job after the update. |
| Other | Stale files that aren't block files | Review each. Real leftovers belong in the delete list (`build-delete-list`). |
| Generated | Leftovers the compiled target also has | Generated by the build (theme CSS, `styles-v2`); not leftovers. |

The package checks (with `-p`):

| Check | Passes when |
|---|---|
| source | The checkout has the same files as the target ref, and the target matches origin. |
| zip | `unzip -t` finds no errors. |
| overrides | No `Themes\*\Styles\_css-overrides.less` or `_variable-overrides.less` for a theme the minimum already has. They hold a site's own theme settings. A theme new since the minimum must ship its override files. |

Per-release file lists are in the output folder. Then tell the packager what to expect when testing: one-time compile
errors for chopped blocks are possible on paths that run a new chop job, and they clear once the job runs.

## Limits

- Only git-tracked RockWeb files are compared, plus the compiled target for generated files. `Bin`, `web.config` and
  theme override files are excluded from the release table.
- Sites already damaged by an earlier bad package aren't modelled. To check one path, treat the damaged site as holding
  release V's copy of the files the bad package missed, then confirm the new package replaces them.

## Known history

- 17.9, 17.10, 18.5, 18.6, 19.5, 19.6 were built from a base other than their minimum. Sites on other allowed versions
  got missing files (e.g. 18.7 sites installing 19.6: GitHub issue 7124).
- 17.12 (min 17.11), 18.8 (min 17.6.1) and 19.8 (min 18.2.4) passed this check built from their minimum. 19.8 was
  tested clean from 18.2.4, 18.8 and 19.7.
- A one-time compile error for a chopped block (e.g. CS0234 in `LavaShortcodeList.ascx.cs`) or the 18.1 kiosk blocks can
  appear right after an upgrade, before the job removes the old files. It clears on its own; confirm the files are gone.
